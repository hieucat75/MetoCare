## 3. Verification verdicts on previously-claimed fixes

> Each verdict answers one question: **is it genuinely closed?**

### A. SEC-F2 — "access token outlives account block/self-delete" (`74742af`)
**VERDICT: GENUINELY CLOSED (with one documented, acceptable edge).**
`current_user()` now performs an indexed PK lookup of `User.is_active` on **every** token-authenticated request and rejects with the *same* generic 401 as a bad token, so a disabled account is not enumerable — `app/api/deps.py:96-105`. Only the boolean column is selected (no PHI loaded). `delete_account` sets `is_active=False` (`app/services/account.py:265`) and revokes refresh tokens (`account.py:229-239`), so self-deletion and admin block both take effect on the next request rather than at token expiry.
*Edge, correctly documented in-code:* a **missing** row is not rejected (`deps.py:100` tests `is_active is False`), which is safe only because there is no hard-delete path — verified: `delete_account` soft-deletes and anonymizes, never `db.delete()` (`account.py:137-267`). Regressions exist and pass: `tests/test_account_export_delete.py:145,160,181`.

### B. PRIV-F1 — "`documents` consent enforced nowhere" (`46d1e0a`, mobile follow-up `6ab3b04`)
**VERDICT: CLOSED FOR THE MDI PIPELINE; NOT CLOSED PLATFORM-WIDE.**
The gate is a genuine single choke point: `_require_documents_consent` is called from `_resolve_patient_id` (`routes/documents.py:78-103`), and **every** patient document endpoint in that router resolves through it — upload-session, qa-fixture, finalize, list, get, file, extraction, candidates, confirm, merge, reject, reprocess (`documents.py:172,209,229,304,318,333,355,381,414,452,490,511`). I checked for a bypass and found none in that router. Signed blob URLs are only minted inside the gated `get_document_file` (`documents.py:325-345`), so revocation stops **new** content access. Fail-closed on absent/revoked/stale-version is proven by `tests/api/test_documents_api.py:135-171` (4-phase: none → grant → revoke → stale).
*Two caveats:* (1) already-issued signed GET URLs remain redeemable for up to 900 s after revocation — **SEC-F14**; (2) the parallel `/lab-uploads` OCR route is **not** gated — **PRIV-F4**. The consent category is named "Tài liệu y tế / OCR" (`consent_policy.py:50-52`), and a patient would reasonably expect it to cover both.

### C. PRIV-F2 — "account deletion never erased storage blobs" (`0da0f06`)
**VERDICT: CLOSED FOR BLOBS. NOT CLOSED FOR ALL PHI.**
Blob-key collection is complete against the model layer: I enumerated every blob-key column in the schema — `MedicalDocument.quarantine_key`/`accepted_key` (`models/medical_document.py:86-87`), `DocumentPage.storage_key` (`:126`), `LabDocument.storage_key` (`models/clinical.py:93`) — and `delete_account` collects **all three families**, across *all* the patient's documents rather than only newly-stamped ones, returning a de-duplicated sorted list (`app/services/account.py:183-215,267`). The route erases post-commit, best-effort and idempotent, logging failures for the orphan sweep (`routes/account.py:106`). Regression `tests/test_account_export_delete.py:207` passes. There is no fourth blob writer: `grep -rn "put_bytes\|get_storage()"` outside `services/storage/` yields only `routes/documents.py`, `routes/account.py`, `services/mdi/service.py`.
*Not closed:* PHI-bearing **child rows** survive erasure — `MetoMessage.content`, `DocumentPage.ocr_raw`, `ExtractionCandidate.fields_json`/`corrections_json` are never stamped or nulled. See **PRIV-F5**.

### D. Default-secret fail-loud guard (`4539a3d`)
**VERDICT: GENUINELY CLOSED.**
`validate_required_env_vars` refuses to start in any env outside `dev|test|local` when `secret_key` starts with the committed dev prefix **or** the committed Fernet key appears **anywhere** in the comma-separated rotation list (not just position 0) — `app/core/config.py:244-262`. It is actually invoked: `app/main.py:43` inside the lifespan, i.e. before serving. `warn_if_insecure` is a *separate*, weaker prod-only warning path (`config.py:307-321`, `main.py:107`) and is not what carries the guarantee. Tests: `tests/test_config_secrets_guard.py` (green in the run above). The same function additionally fail-louds on relaxed auth (`config.py:264-295`) and on the QA-fixture path in prod (`config.py:297-305`).

## 5. NEW findings

### PRIV-F3 — Medical-document images are sent to a cloud OCR vendor with no feature-flag gate, and the path is live on staging · **P0**
**What.** `run_ocr` selects `AzureDocIntelEngine` **whenever `AZURE_DOC_INTEL_KEY` + `AZURE_DOC_INTEL_ENDPOINT` are present**, ahead of local Tesseract, with **no** `FeatureFlag` check — `app/services/ocr_engine.py:479-497` (selection at `:491-492`; credential test at `:256`). `run_ocr` is the default engine of the MDI document pipeline (`app/services/mdi/pipeline.py:20,53-55`), i.e. every prescription/lab/report photo a pilot user uploads. `lab_upload.build_draft` independently does the same "table-first" Azure call for image uploads (`app/services/lab_upload.py:229-236`). The `OCR_CLOUD_FALLBACK` flag only guards `run_cloud_ocr_if_permitted` (`ocr_engine.py:424-449`), a *secondary* zero-biomarker escalation (`lab_upload.py:251-252`) — so the flag is **not** the control it is credited as being.
**Why P0.** The staging deploy sets endpoint **and** key **and** the flag: `.github/workflows/azure-staging.yml:211-214`. This directly contradicts three launch-readiness statements: `00-CURRENT-STATE.md §3` ("`OCR_CLOUD_FALLBACK` **OFF** … no PHI leaves device/region until owner authorizes"), `TRACKING.md` R-05 ("flag OFF + fail-closed; owner authorization required to enable"), and `12-PILOT-OPERATIONS-RUNBOOK.md` ("Real-data mode … cloud OCR stays OFF (local/mock only — no PHI leaves region)"). Any pilot cohort switched to real-data mode would export real medical images to a third-party processor under a written assurance that this cannot happen.
**Exact remediation.**
1. *Code (blocking).* In `ocr_engine.run_ocr`, wrap the Azure branch: `if is_enabled(FeatureFlag.OCR_CLOUD_FALLBACK) and AzureDocIntelEngine.configured():` — and do the same for the table-first branch at `lab_upload.py:229`. Better: introduce a single `_cloud_ocr_permitted()` helper used by all three call sites so there is one choke point, mirroring the PRIV-F1 pattern.
2. *Test (blocking).* Add a regression asserting that with `AZURE_DOC_INTEL_*` set **and the flag off**, `run_ocr` returns a local/Tesseract result (or raises) and **never** constructs `AzureDocIntelEngine` — the current tests do not cover credential-present + flag-off.
3. *Owner/infra (not edited here per the Azure guardrail).* Remove `MCP_FEATURE_OCR_CLOUD_FALLBACK`, `MCP_OCR_CLOUD_PROVIDER`, `AZURE_DOC_INTEL_ENDPOINT` and the `doc-intel-key` secret from the staging container until (a) a data-processing agreement with the vendor exists and (b) the owner authorizes PHI-to-cloud in writing, as the credential-readiness standing rule requires.
4. *Docs.* Until 1–3 land, correct `TRACKING.md` R-05 and the runbook: staging **does** send document images to Azure DI.

### PRIV-F4 — `documents` consent is not enforced on the legacy lab-upload OCR route · **P1**
**What.** `POST /lab-uploads` accepts a lab image/PDF/URL, OCRs it and returns extracted values, with role + flag + rate-limit checks but **no consent check** — `app/api/v1/routes/lab_upload.py:41-53`. The PRIV-F1 choke point lives in the *documents* router only. A patient who revokes "Tài liệu y tế" is still fully OCR-processed through this path (and, per PRIV-F3, still cloud-egressed).
**Remediation.** In `create_lab_upload_draft`, immediately after the flag check, call the same gate: `if not is_granted(db, user.id, CATEGORY_DOCUMENTS): raise ConsentDenied(...)` (reuse the message from `routes/documents.py:88-91`; the global handler already maps it to 403 `CONSENT_DENIED`, `app/main.py:136-141`). Add a `@pytest.mark.real_consent` regression mirroring `tests/api/test_documents_api.py:135`.

### SEC-F10 — Rate limiting is keyed on the ingress proxy address, collapsing all clients into one bucket · **P1**
**What.** `_client_key` returns `request.client.host` (`app/api/deps.py:35-36`). The app is served by `gunicorn -k uvicorn.workers.UvicornWorker` with **no** `--forwarded-allow-ips` (`backend/startup.sh:12-21`, `backend/Dockerfile:46`) and no `FORWARDED_ALLOW_IPS` anywhere in the repo or workflows (grep: no hits), so the default trusted-proxy list (`127.0.0.1`) does not include the ACA ingress hop and `X-Forwarded-For` is discarded. Every request therefore shares one key per action, against `ratelimit_auth_capacity = 20` per 60 s (`config.py:209-210`).
**Impact (both directions).** (a) *Availability:* 20 logins/minute for the **entire** pilot cohort — one retry loop 429s everyone. (b) *Security:* per-client throttling on `/auth/login`, `/auth/register`, document upload and `/lab-uploads` (a synchronous OCR CPU sink) is not actually per-client. Account lockout is unaffected — it is keyed on the login identifier (`routes/auth.py:103`, `core/ratelimit.py:57-80`) — so credential stuffing against a single account is still bounded.
**UNVERIFIED (runtime confirmation).** `curl -H "X-Forwarded-For: 203.0.113.9" https://<staging-fqdn>/api/v1/health -i` twice from two networks and compare the access-log `client` value, or hammer `/auth/login` from two devices and see whether the 429 is shared.
**Remediation.** Configure the trusted hop (`--forwarded-allow-ips=<ACA ingress CIDR>` or `FORWARDED_ALLOW_IPS`) **and** derive the key from the right-most untrusted `X-Forwarded-For` entry, falling back to `request.client.host`; where the caller is authenticated, prefer `f"{action}:{user_id}"`. Add a unit test asserting two distinct XFF values get independent buckets. This is orthogonal to the known PROD-F3/SEC-F8 (memory backend is single-replica-only) — fixing one does not fix the other.

### PRIV-F5 — GDPR erasure leaves PHI-bearing child rows behind · **P1**
**What.** `delete_account` erases blobs and soft-deletes parents but never touches the rows that actually hold the text: `MetoMessage.content` (free-text patient symptoms + AI answers quoting labs/meds — `models/meto.py:61-88`) survives, because only the parent `MetoConversation` is stamped (`app/services/account.py:217-227`); `DocumentPage.ocr_raw` + `blocks_json` (`models/medical_document.py:126-129`) and `ExtractionCandidate.fields_json` + `corrections_json` (`models/medical_document.py:175,181`) survive, because only `MedicalDocument` is stamped (`account.py:185-198`). The export bundle deliberately omits message content (`account.py:348-357`), so the data is neither exportable nor erasable — the worst combination for a data-subject request.
**Remediation.** Extend `delete_account` (keeping the pure-function + idempotent shape it already has): for the user's conversations set `MetoMessage.content = ""` and null `tool_calls`/`tool_results`; for the patient's documents null `DocumentPage.ocr_raw`/`blocks_json` and `ExtractionCandidate.fields_json`/`corrections_json` (retain row skeletons so promotion-idempotency and audit joins still resolve). Extend `tests/test_account_export_delete.py` with an erasure-completeness assertion that re-queries each child table after deletion.

### SEC-F11 — Meto chat message bodies (and OCR candidate fields) are PHI stored unencrypted, against the platform's own standard · **P1**
**What.** `MetoMessage.content: Mapped[str] = mapped_column(Text, ...)` — `app/models/meto.py:75`. Every other free-text PHI column in the system uses `EncryptedString`, **including the older AI conversation model** (`app/models/ai.py:44,91`) and OCR raw text (`models/medical_document.py:128`), so this is an inconsistency rather than a deliberate policy. `ExtractionCandidate.fields_json` (`:175`) — extracted drug names, doses, diagnoses — is likewise plaintext JSON while the page text it was derived from is encrypted.
**Remediation.** Change `MetoMessage.content` to `EncryptedString(on_decrypt_failure="none")` plus a data migration re-encrypting existing rows; verified safe because nothing queries or indexes `content` by value (`grep -rn "MetoMessage.content"` shows reads/writes only). For `fields_json`, either encrypt or record an explicit, owner-signed accepted-risk note in this file — do not leave it undocumented.

### SEC-F12 — `/metrics` is unauthenticated on an externally-exposed ingress · **P2**
`app/main.py:181-185` serves the Prometheus text exposition with no auth, gated only by `metrics_enabled` — which staging sets true (`azure-staging.yml:210`) on an `--ingress external` container app (`azure-staging.yml:227`). No PHI is exposed (labels are route templates + status codes, `app/core/metrics.py:16-20,57-72`), but it hands an unauthenticated caller the full route inventory, traffic volume, error and latency profile. **Remediation:** restrict via ACA ingress IP rules, or require a shared token header on `/metrics`, or set `MCP_METRICS_ENABLED=false` and scrape from inside the environment.

### SEC-F13 — Android backup posture is not source-controlled and defaults to backup-enabled · **P2**
The generated release manifest carries `android:allowBackup="true"` with `fullBackupContent="@xml/secure_store_backup_rules"` and `dataExtractionRules="@xml/secure_store_data_extraction_rules"` — but **those resources do not exist** (`mobile/android/app/src/main/res/xml/` is absent) and `android/` is gitignored (`mobile/.gitignore:13`), so the intended exclusions live nowhere in version control and the current prebuild output would not even link. `mobile/app.config.ts` declares `blockedPermissions` (WS11-F3, correctly applied) but says nothing about backup. Practical exposure is low — expo-secure-store values are wrapped by Keystore keys that are not backed up — but a PHI app should state its posture. **Remediation:** set the backup policy in `app.config.ts` (`android.allowBackup: false`, or ship the two XMLs via a config plugin) so every `prebuild` reproduces it.

### SEC-F14 — Signed blob GET URLs survive consent revocation and account deletion for their full TTL · **P2**
`verify_blob_token` validates signature + op + expiry only; the token binds a key, not a subject or a document state (`app/services/storage/signing.py:76-103`), and `blob_get` performs no DB lookup (`routes/documents.py:278-294`). With `storage_download_url_ttl_seconds = 900` (`config.py:91`), a URL minted just before revocation/deletion stays redeemable for up to 15 minutes. **Remediation:** embed `document_id` in the token and have `blob_get` verify the document is still live and consent still granted, or cut the GET TTL to ~60 s (the mobile viewer loads immediately after issuance).

**Not re-raised (already in the confirmed register, re-verified as still-true):** PROD-F1 ephemeral storage (`azure-staging.yml:209`), PROD-F3/SEC-F8 in-memory limiter, PROD-F4 auth env outside version control (confirmed: `MCP_MFA_ENFORCEMENT_ENABLED` / `MCP_ALLOW_RELAXED_AUTH` appear nowhere in `azure-staging.yml`), PROD-F5 retention job, SEC-F3 register-enumeration 409 (`routes/auth.py:74-75`), SEC-F5 SSRF DNS-rebinding TOCTOU, SEC-F7 JWT without `iss`/`aud`, WS5-F1/F3 no aggregation.

## 6. Verdict

| Gate | Security & privacy position |
|---|---|
| **Internal pilot (synthetic data only)** | 🟡 **GO with conditions** — PRIV-F3 must be either fixed in code or accepted in writing *and* the affected docs corrected; SEC-F10 should be fixed before the cohort exceeds a handful of concurrent users (shared bucket = shared 429). |
| **Controlled pilot with any real patient data** | ⛔ **NO-GO until PRIV-F3 is closed.** Real medical images would leave the cluster to a third-party processor while three launch documents assert the opposite. PRIV-F4 and PRIV-F5 should close alongside it. |
| **Public beta / production** | ⛔ unchanged — the pre-existing infra P0s (PROD-F1, PROD-F2) plus PRIV-F3/PRIV-F5/SEC-F10/SEC-F11 above. |

Authentication, session lifecycle, BOLA, input validation, SSRF, backend log hygiene and mobile secret storage are, on inspection, **materially above the norm for a pre-launch product** — the failures found are concentrated in *egress* and *erasure completeness*, not in the access-control core.
