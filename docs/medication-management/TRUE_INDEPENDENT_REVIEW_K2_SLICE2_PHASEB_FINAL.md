## 6. Detailed Findings

### Finding 1 (P1) — The transition-history table's central "no ordinal column needed" claim is false as specified: order and completeness are not actually DB-enforced

- **Severity:** P1 (per this review's explicit mandate in Review Area 4: if complete-history integrity cannot be guaranteed without an ordinal/uniqueness/deferred constraint, this MUST be reported as P1).
- **Plan line range:** §3.4, lines 291–314 (table schema, columns, and the "No `sequence_number`/ordinal column is added" reasoning paragraph, lines 304–310); §3.6, lines 336–344 (the one trigger, `trg_k2s2_ingestion_attempt_transitions_ordered`, that exists for this table).
- **Repository evidence:** `backend/alembic/versions/k2_s0_integrity_guards.py:150–158, 253–256` — the precedent table (`knowledge_lifecycle_transitions`) this plan claims to mirror in shape and enforcement idiom (plan §3.4, unchanged-from-Fix-Round-1 text) has an explicit **pair-level CHECK constraint**, `ck_knowledge_lifecycle_transitions_pair`, restricting `(from_status || '->' || to_status)` to a closed list of legal pairs. `ingestion_attempt_transitions` (plan §3.4, columns table, lines 297–302) has **no equivalent constraint** — `from_status` and `to_status` are each independently checked against the same 5-value vocabulary, but no constraint anywhere restricts which *pairs* are legal. There is also no `UNIQUE(attempt_id, from_status, to_status)` or any other constraint limiting how many rows, or which rows, may exist per `attempt_id`.
- **Concrete failure scenario and case-by-case walk (all 14 required cases):**

  | # | Case | Blocked? | Mechanism (or why not) |
  |---|---|---|---|
  | 1 | No transition rows at all for a terminal attempt | **NOT BLOCKED** | Nothing ties `ingestion_attempts` row existence to any minimum count of child rows. A raw-SQL insert of the attempt row alone succeeds. |
  | 2 | Only the terminal transition present (missing earlier hops) | **NOT BLOCKED** | A single row (`from_status=NULL, to_status='staged'`) passes both column CHECKs (NULL is unconditionally legal for `from_status`; `'staged'` is in the `to_status` vocabulary) and the ordering trigger (no prior sibling to violate, not later than `completed_at`). |
  | 3 | Duplicate `received→validated` rows | **NOT BLOCKED** | No uniqueness constraint on `(attempt_id, from_status, to_status)`. Both rows share the same `occurred_at` in normal operation (§5: one captured `now`), so the ordering trigger's "earlier than existing MAX" condition is never true for the duplicate (equal is not less-than) — it silently accepts the duplicate. |
  | 4 | Two terminal transitions for the same attempt (two rows both `to_status` ∈ terminal set) | **NOT BLOCKED** | Same reasoning as #3 — nothing detects or rejects a second terminal-shaped row. |
  | 5 | Direct `received→staged` (skipping `validated`) | **NOT BLOCKED** | Without a pair-level CHECK, `received` and `staged` are each individually legal vocabulary values; the pair itself is never validated. |
  | 6 | `validated→validated` (illegal self-loop per §4.1's own table) | **NOT BLOCKED** | Same root cause — no pair CHECK. |
  | 7 | `received→validated` then `received→rejected` for the same attempt (a fork) | **NOT BLOCKED** | Nothing prevents two rows sharing the same `from_status`; this is exactly the case a real ordinal/uniqueness design would catch and this plan's design cannot. |
  | 8 | Transition history's own final `to_status` differs from the parent attempt's `status` column | **NOT BLOCKED**, and structurally worse than it looks | No CHECK/trigger cross-references `ingestion_attempts.status` against any transition row at all. Worse: because every row for one attempt shares the identical `occurred_at` in normal operation (§5), "the final row" is not even a well-defined concept from stored data alone — there is no tiebreaker. |
  | 9 | Transition row referencing the wrong `attempt_id` (belongs to a different attempt than context implies) | **NOT BLOCKED** (inherent limitation, not fully fixable by a plain CHECK) | The FK only requires *some* existing `ingestion_attempts.id`; nothing ties a transition row's `attempt_id` to the *specific* attempt whose history it's meant to belong to beyond the FK itself. Noted for completeness, not counted as an aggravating factor beyond #1–#8. |
  | 10 | Transition timestamps that decrease across rows for the same attempt | **BLOCKED** | The `trg_k2s2_ingestion_attempt_transitions_ordered` trigger's first condition (`occurred_at < MAX(existing for same attempt_id)`) correctly fires. |
  | 11 | First transition timestamped before the parent attempt's `created_at` | **NOT BLOCKED** | The trigger only checks against sibling rows' MAX `occurred_at` (empty on the first row, trivially passes) and against `completed_at` as an *upper* bound — there is no lower-bound check against `created_at` anywhere in §3.3's or §3.4's constraints. |
  | 12 | Terminal transition timestamped after the parent's `completed_at` | **BLOCKED** | The trigger's second condition (`occurred_at > parent.completed_at`) correctly fires, and the flush-ordering claim (attempt row flushed before its transition rows, so the trigger can read the parent's `completed_at` mid-transaction) is verified correct: SQLAlchemy's unit-of-work topologically orders INSERTs by FK dependency regardless of `session.add()` call order, so this part of §3.4/§5's design is sound. |
  | 13 | Equal timestamps across multiple transitions for the same attempt — does the trigger even fire, and is that a loophole? | **Trigger never fires; this is the root cause, not a separate bug** | The plan's own text (§3.4, lines 309–310) explicitly acknowledges "this trigger never actually fires" in normal operation, framing it as harmless "genuine DB-level insurance." It is not harmless: equal timestamps are also exactly the condition under which duplicates (#3) and forks (#7) both slip through, because the *only* enforcement mechanism this table has is timestamp-based, and normal-operation timestamps are always equal. The trigger provides real protection only against a narrow, contrived out-of-order-write threat (#10/#12) and zero protection against the structural-integrity threats (#1–#9) that Review Area 4 is actually about. |
  | 14 | Insertion in reverse statement order within the same transaction (terminal row inserted before earlier hops) | **NOT BLOCKED** | With no ordinal column and identical timestamps, physical insertion order is unrecoverable from stored data and the trigger cannot distinguish it from correct order. |
  | 15 | Raw-SQL insertion of an additional transition row **after** the parent attempt has already committed, in a separate, later transaction | **NOT BLOCKED** | An attacker/bug can set the new row's `occurred_at` exactly equal to the already-recorded `completed_at` (or to the existing MAX). Neither trigger condition is a strict violation at equality (`<` and `>`, not `<=`/`>=`), so the insert is accepted. This directly undermines the "immutable, complete" audit-trail claim in §18 (which addresses only tampering with *existing* rows via the separate no-UPDATE/no-DELETE triggers, not *appending* a new, contradictory row well after the fact). |

  **Net result:** 11 of the 14 required cases (1, 2, 3, 4, 5, 6, 7, 8, 11, 14, 15 — with 9 and 13 as structural/root-cause notes) are **not blocked** by anything in the plan's proposed schema. Only 10 and 12 are genuinely enforced.
- **Expected invariant:** exactly one valid, complete transition history exists per terminal attempt — no more, no less — recoverable and verifiable from stored data alone, per this review's Area 4 requirement.
- **What the plan currently says:** "the correct order of any attempt's 2-or-3-row walk is already uniquely and fully recoverable from the `(from_status, to_status)` pair values alone... Adding a redundant ordinal column would duplicate information the closed vocabulary already encodes" (§3.4, lines 304–310). This claim is false as specified, because the "closed vocabulary" it depends on is never actually enforced as a *pair* constraint anywhere in the schema — only as two independent single-column constraints, which is a materially weaker guarantee.
- **Minimal correction:** the cheapest complete fix is two additions to §3.4, not a full redesign:
  1. Add a pair-level `CHECK`, mirroring the precedent exactly: `CHECK ((COALESCE(from_status,'') || '->' || to_status) IN ('->received','received->validated','received->rejected','validated->unresolved','validated->staged'))` (or equivalent NULL-safe construction) — this alone closes cases 5, 6, and narrows 7/8.
  2. Add either (a) a `sequence_number SMALLINT NOT NULL` column with `UNIQUE(attempt_id, sequence_number)`, assigned by a DB trigger the same way Slice 0's `knowledge_ai_generations.sequence_number` already is, or (b) a `UNIQUE(attempt_id, from_status, to_status)` constraint plus a trigger on the *parent* `ingestion_attempts` INSERT that validates the exact expected set of transition rows already exists for that `attempt_id` before allowing the parent row's own insert to succeed (feasible since, per §5, the transition rows are constructed and flushed in the same statement batch). Either closes cases 1–4, 7, 9, 14, 15.
  3. Add a CHECK or trigger tying the transition history's terminal `to_status` to `ingestion_attempts.status` for the same `attempt_id` (closes case 8).
  4. Change the ordering trigger's bounds to include a lower-bound check against `created_at`, not only an upper bound against `completed_at` (closes case 11), and change `<`/`>` to `<=`/`>=` semantics deliberately considered (case 13/15) — or, more robustly, make the equality-permitting design intentional but pair it with the uniqueness fix above so equal timestamps can no longer hide duplicates/forks.

### Finding 2 (P1) — Both proposed Phase C migration revision IDs exceed Alembic's actual `version_num` column width (32 chars) and will fail on PostgreSQL — this is the exact bug class that has already broken a production deploy in this codebase

- **Severity:** P1 — blocks Phase C; would fail CI's own Postgres job and any real deployment, though it fails loudly rather than corrupting data.
- **Plan line range:** §10, line 578–581 (migration table: `k2_s2_ingestion_registry_and_artifacts`, `k2_s2_ingestion_attempts_and_history`); §14, lines 636–637 (file paths repeating the same two ids).
- **Repository evidence:** installed `alembic==1.18.4` package, `alembic/ddl/impl.py:173`: `Column("version_num", String(32), nullable=False)` — the authoritative, currently-installed width of `alembic_version.version_num`. Independently verified against this repo's own migration chain: scanning all 73 files under `backend/alembic/versions/*.py` for their `revision =`/`revision: str =` value, the **longest existing revision id in the entire chain is 31 characters** (`t10_m1_consultation_marketplace`) — every single migration ever written in this repository has respected the 32-char limit, whether by convention or by a prior lesson learned. `k2_s2_ingestion_registry_and_artifacts` is **38 characters**; `k2_s2_ingestion_attempts_and_history` is **36 characters** — both exceed the column width by 6 and 4 characters respectively.
- **Concrete failure scenario:** SQLite does not enforce `VARCHAR`/`String` length limits by default (dynamic typing, TEXT affinity ignores declared length), so `alembic upgrade head` with either oversized revision id would succeed silently on SQLite — including in any SQLite-based local dev/test run and any SQLite-based CI step. PostgreSQL genuinely enforces `VARCHAR(32)`; the first `INSERT`/`UPDATE` of `alembic_version.version_num` with either 36- or 38-character value would fail with `value too long for type character varying(32)`, breaking `alembic upgrade head` on the PostgreSQL CI job (`.github/workflows/ci.yml`'s `test-backend-postgres`, which the plan's own §13 "CI Option A" explicitly requires exercising Postgres migrations) and any real staging/production deploy that runs migrations. This is not a hypothetical risk — the user's own project memory records this exact defect class already causing a failed production deploy in this codebase (Doctor Portal P0, PRs #88–#93: "First deploy failed on oversized Alembic revision id (SQLite-invisible, Postgres-only bug) → hotfixed in #93 + regression test added"), meaning this specific failure mode has a known precedent and a known regression test in this very repo that evidently was not consulted while drafting this plan's migration ids.
- **Expected invariant:** every Alembic revision id must fit within `alembic_version.version_num`'s actual column width (32 characters) on PostgreSQL.
- **What the plan currently says:** the plan's own §11 review-area checklist (per this review's own instructions) explicitly calls for this exact check, but the plan document itself never states or verifies the revision-id lengths anywhere — it simply proposes the two ids without any length discussion.
- **Minimal correction:** shorten both ids to ≤32 characters while keeping them descriptive and collision-free against the existing chain, e.g. `k2_s2_registry_artifacts` (24 chars) and `k2_s2_attempts_history` (22 chars). Add an explicit one-line CI or pre-merge check (`len(revision) <= 32` for every file under `alembic/versions/`) referencing the PR #93 precedent, so this class of defect cannot recur silently again.

### Finding 3 (P1) — §18's Security Threat Model overclaims what `triggered_by_user_id` actually mitigates: it prevents forgery of a nonexistent/reserved value, not genuine impersonation of a real user

- **Severity:** P1 — a security-threat-model section making an inaccurate mitigation claim, in a document whose entire purpose is a go/no-go security judgment, is a real documentation-accuracy defect, not merely cosmetic; Review Area 9 explicitly instructs reviewing this field "honestly and skeptically."
- **Plan line range:** §18, lines 719–727 (threat row: "Forged/impersonated initiator identity... `triggered_by_user_id` is a real FK, resolved and validated pre-attempt... never used for any authorization decision — purely an audit field"); §6, lines 500–510 ("Records the *initiator*... `triggered_by_user_id` is the human (if any) who ran the CLI").
- **Repository evidence:** not a repository-code gap (no Slice 2 code exists yet to test) — this is a design-claim-vs-design-mechanism mismatch, verifiable purely by reading the plan's own CLI contract (§7, lines 519–544) and pre-attempt gate description (§4.6, lines 399–412) side by side. Neither section describes, nor could describe (no HTTP surface, no session/auth token, per §1's own non-goals), any mechanism that authenticates the CLI invoker against the `--triggered-by-user-id` value supplied. The pre-attempt gate only checks (a) the value is not a forged `system:` namespace string, and (b) the value resolves to *some* existing row in `users`. Neither check has anything to do with proving the operator running the CLI *is* that user.
- **Concrete failure scenario:** any operator with local CLI access (the only access this dormant slice ever grants, by design) can pass any other real user's UUID as `--triggered-by-user-id` — a doctor's id, an admin's id, anyone's — and the resulting `ingestion_attempts` row will show that other person as the "initiator," fully FK-valid, fully passing every check in §3.3/§4.6, with the plan's own §6 prose asserting flatly that this column "is the human... who ran the CLI." If this audit trail is ever consulted for an incident review (its stated purpose), it would be trusted as more authoritative than it actually is.
- **Expected invariant:** a Security Threat Model section's stated mitigations must match what the described mechanism actually proves; residual risk that is *not* mitigated must be disclosed, not implied away by confident language ("the human... who ran the CLI").
- **What the plan currently says:** frames the threat as "Forged/**impersonated**" and states it is "mitigated" by the FK, without ever disclosing that genuine impersonation (a real, valid, borrowed id) is explicitly out of scope and unaddressed.
- **Minimal correction:** rename the §18 threat row to "Forged/nonexistent initiator identity" (drop "impersonated," since that case is not actually addressed), and add one explicit residual-risk sentence, e.g.: *"`triggered_by_user_id` is operator-supplied, self-reported input — the FK proves only that the referenced user exists, never that the CLI's invoker is that user. Slice 2 has no mechanism to authenticate the CLI invoker; this field is trusted, unauthenticated audit input only, consistent with the CLI's local-operator-trust threat model (§1) — never used for any authorization decision."* Soften §6's "is the human (if any) who ran the CLI" to "records the human identity claimed for this invocation (self-reported, not authenticated)."

### Finding 6 (P2) — §3.6 does not specify `FOR EACH ROW` vs `FOR EACH STATEMENT`, or `TG_OP` branching, for the shared PostgreSQL immutability function used across UPDATE/DELETE/TRUNCATE
